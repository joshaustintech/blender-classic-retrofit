# Post-2.45 backports and safe Rust opportunities

Research date: 2026-10-14. Baseline: repository `215b1633ee0`, Blender 2.45 retrofit. Research only; no implementation or performance measurements performed.

## Decision

Start with small upstream fixes still present in this tree: packed-file descriptor cleanup, 21-character ID termination, FreeType failure handling, Python traceback lifetime, and quaternion dot-product correctness. Profile text reading and image kernels next. Do not import the 2.49 renderer or assume Rust makes the same algorithm faster.

[CONTEXT.md](../../CONTEXT.md) requires the original interface, scripts, and Blender Internal rendering. Therefore distinguish a deliberate bug correction from a behavior-preserving optimization: a corrected bug can intentionally change previously wrong output, and requires a reviewed fixture exception. Rust or SIMD replacements must preserve approved semantics and fidelity. The game engine is outside this native-build scope; its advertised speed gains do not apply.

### Where faster safe Rust is plausible, and where it is not yet justified

Safe Rust is not inherently faster than optimized C. Both can feed LLVM's vectorizers; inspect the already optimized C assembly and profile the actual workload before selecting a language change. LLVM describes both loop and straight-line vectorization; profitability, aliasing and reductions affect the generated result. [LLVM vectorizers](https://llvm.org/docs/Vectorizers.html), [Rust std::arch auto-vectorization example](https://doc.rust-lang.org/std/arch/index.html).

| Candidate | Possible performance mechanism (hypothesis) | Why it is a bounded seam | Required evidence |
|---|---|---|---|
| RGBA/ABGR channel permutation, row fills and integer pixel blends | Batch contiguous pixels, eliminate repeated dispatch, vectorize permutations/arithmetic. | Local inputs/outputs, no scene traversal. [imageprocess.c](https://github.com/joshaustintech/blender-classic-retrofit/blob/215b1633ee0dea2f83ed2dc1da86264f47d3898d/source/blender/imbuf/intern/imageprocess.c#L47), [rectop.c](https://github.com/joshaustintech/blender-classic-retrofit/blob/215b1633ee0dea2f83ed2dc1da86264f47d3898d/source/blender/imbuf/intern/rectop.c#L46). | Exact output, generated vector instructions, throughput across sizes; include buffer conversion/transfer cost. Large permutations may be memory-bandwidth bound. |
| `addAlphaOverFloat`, `addAlphaUnderFloat`, `addalphaAddFloat` | SIMD across independent pixels; separate non-overlapping destination ownership may aid vectorization. | Preserve existing formula per pixel, avoid cross-pixel reductions. [pixelblending.c](https://github.com/joshaustintech/blender-classic-retrofit/blob/215b1633ee0dea2f83ed2dc1da86264f47d3898d/source/blender/render/intern/source/pixelblending.c#L74). | Alpha/HDR edge cases and identical operation ordering, then scene/pass comparisons. Ownership alone does not prove end-to-end gains. |
| Image filters/scaling and compositor filters | Process independent output pixels/rows in batches, improve contiguous access and reuse intermediates. | Existing filter definitions can be retained; an out-of-place kernel is easier to own safely than an in-place sweep. [filter.c](https://github.com/joshaustintech/blender-classic-retrofit/blob/215b1633ee0dea2f83ed2dc1da86264f47d3898d/source/blender/imbuf/intern/filter.c#L48), [scaling.c](https://github.com/joshaustintech/blender-classic-retrofit/blob/215b1633ee0dea2f83ed2dc1da86264f47d3898d/source/blender/imbuf/intern/scaling.c), [CMP_filter.c](https://github.com/joshaustintech/blender-classic-retrofit/blob/215b1633ee0dea2f83ed2dc1da86264f47d3898d/source/blender/nodes/intern/CMP_nodes/CMP_filter.c). | Preserve filter taps, border rules, color space, alpha treatment and rounding. Calling a helper once per vertex likely loses to call/IPC overhead. |
| Ray intersection/traversal (`intersection`, `testnode`, `d3dda`) | Owned indexed acceleration structures can reduce pointer chasing; independent ray packets may enable SIMD. | This is a later, substantial renderer project, not a small replacement. [ray.c](https://github.com/joshaustintech/blender-classic-retrofit/blob/215b1633ee0dea2f83ed2dc1da86264f47d3898d/source/blender/render/intern/source/ray.c#L808). | Intersection tie-breaking, epsilon rules, traversal ordering, transparency/refraction/shadows, RNG order and complete scene corpus. Preserve the existing spatial structure/algorithm first. A different BVH or sampler cannot be presumed visually identical. |

## What “safe Rust with SIMD” permits

The current [.scratch native-build spec](../../.scratch/macos-native-build/spec.md) requires optional Rust to be safe and standard-library-only. There is no existing Rust crate with an enforced `forbid(unsafe_code)` gate; that lint is the proposed way to make the constraint mechanically reviewable.

1. **Stable Rust + stdlib + no authored unsafe:** start with safe scalar slice/array loops and LLVM auto-vectorization. This can produce SIMD, but verify assembly on the actual Apple Silicon target. It does not guarantee either SIMD or a gain over the C baseline. [Rust std::arch](https://doc.rust-lang.org/std/arch/index.html), [LLVM](https://llvm.org/docs/Vectorizers.html).
2. **Explicit portable SIMD:** current official `std::simd` documentation still labels it nightly-only (`portable_simd`). Safe value operations can form an owned-buffer kernel, but nightly is a policy/toolchain change and pointer APIs must be avoided. This is an option to investigate, not silently adopt. [Rust portable SIMD](https://doc.rust-lang.org/std/simd/index.html).
3. **Native NEON intrinsics / SIMD crates:** vendor intrinsics commonly require unsafe calls and feature preconditions. A crate with a safe facade can hide unsafe internals; that is a different safety/dependency policy, not proof of a zero-unsafe implementation. No third-party crate is proposed as accepted here. [Rust std::arch](https://doc.rust-lang.org/std/arch/index.html).
4. **C integration:** converting an arbitrary C pointer into a Rust slice is explicitly unsafe and has allocation, alignment, lifetime and aliasing preconditions. Exporting a conventional named C symbol also uses unsafe attributes under current Rust rules. Thus ordinary in-process zero-copy C↔Rust does not satisfy strict `forbid(unsafe_code)` throughout authored Rust. A safe core behind an audited unsafe bridge is possible only if the project changes that policy. [from_raw_parts](https://doc.rust-lang.org/std/slice/fn.from_raw_parts.html), [Rust ABI](https://doc.rust-lang.org/reference/abi.html), [unsafe_code lint](https://doc.rust-lang.org/rustc/lints/listing/allowed-by-default.html#unsafe-code).
5. **Strict-policy integration option:** a bundled Rust helper using `std::io` and owned buffers can keep authored Rust safe. Batch requests with a bounded binary protocol through ordinary pipes/files; preserve cancellation, errors and progress through the original UI. This is an architectural inference, not a completed design. Measure startup, copies and transfer as part of elapsed time; it is unsuitable for per-pixel/per-ray calls and may erase a kernel speedup. The standard library/compiler/OS remain trusted dependencies and contain implementation-level unsafe code. [Rust IO](https://doc.rust-lang.org/std/io/index.html).

### Fidelity constraints for SIMD and parallel work

- **First target exact operations:** channel permutation and integer kernels are the strongest starting candidates. Preserve byte signedness (`CMake/macos.cmake` sets `-funsigned-char`), clipping, saturation, integer width and division rounding. Existing `blend_color_mix` explicitly documents that `/255` and `>>8` are different and that the latter darkens repeated blends; do not use the cheaper expression. [rectop.c](https://github.com/joshaustintech/blender-classic-retrofit/blob/215b1633ee0dea2f83ed2dc1da86264f47d3898d/source/blender/imbuf/intern/rectop.c#L46), [build flags](../../CMake/macos.cmake).
- **Float lanes:** preserve `f32` versus `f64`, expression grouping, branch conditions, signed zeros, exceptional values and subnormals. Rust's `mul_add` rounds once and can differ from separate multiplication/addition; do not introduce it casually. Transcendental precision can vary by platform/toolchain. [Rust f32](https://doc.rust-lang.org/std/primitive.f32.html#method.mul_add).
- **No “fast math” shortcut:** never substitute approximate reciprocal/rsqrt or reorder sums merely for throughput. Vectorize independent pixels/rays before touching sample accumulation/reductions. Floating reductions can require algebraic relaxation for LLVM vectorization; that relaxation conflicts with a strict fidelity claim. [LLVM reductions](https://llvm.org/docs/Vectorizers.html#reductions).
- **Parallel execution:** give workers disjoint output tiles, keep each pixel's accumulation order and sample seed/consumption stable, and merge in deterministic order. Random and ray routines show why scheduling is observable in render output; race freedom alone does not establish deterministic images. [rand.c](https://github.com/joshaustintech/blender-classic-retrofit/blob/215b1633ee0dea2f83ed2dc1da86264f47d3898d/source/blender/blenlib/intern/rand.c#L83), [ray.c](https://github.com/joshaustintech/blender-classic-retrofit/blob/215b1633ee0dea2f83ed2dc1da86264f47d3898d/source/blender/render/intern/source/ray.c).

## Recommended experiment order and acceptance gates

This sequence is a recommendation inferred from the source boundaries, not a speed ranking established by profiling.

1. Reproduce and backport the smallest source-verified upstream correctness fixes. Keep a bug's intended corrected behavior separate from compatibility with a historically incorrect result; render bug fixes can intentionally change pixels even while preserving UI.
2. Profile the current optimized native executable using representative editing, texture, compositing and render workloads. Record inclusive CPU time, allocations, peak memory and latency; select work based on actual attributable cost.
3. Establish a safe owned-buffer Rust oracle for RGBA channel conversion or an exact integer blend, without integrating it. Compare against the C kernel on odd lengths, tails, overlap cases and adversarial values.
4. Compare optimized C, stable safe Rust scalar/auto-vectorized Rust, and (only if explicitly accepted) a pinned nightly safe portable-SIMD variant. Use identical inputs, compiler/target settings and allocation strategy. Show emitted vector instructions and transfer-inclusive end-to-end timings, not just a microbenchmark of arithmetic.
5. Require exact decoded bytes for integer transformations. For float changes use the repository's fixed pre-agreed scene/pass limits; do not widen limits after seeing a regression. Corpus includes HDR/alpha, filters/borders, degenerate triangles, shadow/refraction/transparent materials, motion blur/animation, sampling/RNG and repeated/cancelled renders, with identical settings and seeds. The original reference corpus remains an open gate; a C baseline in this checkout can establish a local regression oracle but cannot certify original-release parity. [Render ADR](../adr/0002-render-parity.md), [scope](../../.scratch/macos-native-build/spec.md).
6. Integrate only after the safety-boundary policy and measurement show a worthwhile total gain; verify unchanged Python API, interaction, file round trips, errors, cancellation and progress. Defer full ray traversal, shading, SSS, simulation and renderer ownership changes until their own profiling and parity gates exist. [Boundary ADR](../adr/0004-preserve-renderer-and-port-platform-boundaries.md).
